# DHA Works Admin Portal

The staff web portal of **DHA Works**, a home-services marketplace for DHA Karachi. DHA staff use it to verify workers and residents, handle reports and disputes, follow every job from request to cash paid, manage users, reviews and settings, and keep an audit trail.

This repository holds only the portal. The database (Supabase migrations, row-level security, RPC functions, tests), the worker app and the product documents live in [DHA-Works-Platform](https://github.com/abdullah-automates31/DHA-Works-Platform); the customer app is a separate repository. The portal talks to the same Supabase project as both apps, **as the signed-in staff member** (never with the service-role key), and every rule that matters is enforced in the database, not here.

## Stack

Next.js 16 (App Router, server actions) and TypeScript, `@supabase/ssr` for cookie sessions, Cloudflare Turnstile for the bot check. No client-side Supabase client: all data access happens on the server.

## Sign-in and security in one paragraph

Staff sign in with email and password (plus a Turnstile check), then a six-digit code **emailed** to them (the Edge Function `admin-2fa` of the platform project sends it; valid 10 minutes). Sensitive actions (suspending, deciding or reopening applications, settings and more) ask for a new emailed code every 15 minutes. Cookies are HttpOnly, the Content-Security-Policy uses a per-request nonce, every page and action calls `requireAdmin()`, and every admin database function checks `is_admin()` and writes an audit row. Details: [docs/ADMIN-PORTAL.md](docs/ADMIN-PORTAL.md) and the security notes in the platform repository.

## Run it locally

```bash
npm install
cp .env.example .env.local        # then fill in the values (see below)
npm run dev                        # http://localhost:3000
```

| Script | What it does |
| --- | --- |
| `npm run dev` / `build` / `start` | Next.js dev server, production build, production server |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run lint` | ESLint |
| `npm test` | unit tests (`node --test`, no network) |
| `npm run types:sync -- <file>` | replace the vendored database types (see below) |

Local testing against a local Supabase stack (fake staff, codes from the function log, the attack drill) is described in `docs/ADMIN-PORTAL.md` and lives in the platform repository's `scripts/` and `supabase/dev/`.

## Environment variables

Only names are listed here; real values are never committed (`.env*` is ignored, `.env.example` holds placeholders).

| Name | Where | Notes |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | browser and server | project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | browser and server | the public anon key |
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | browser | Cloudflare Turnstile site key (public) |
| `TURNSTILE_SECRET_KEY` | **server only** | a production build without it refuses every sign-in (fails closed) |
| `IDLE_LIMIT_SECONDS` | server, optional | tests only: turns the idle logout on (5 to 1800 s); off by default |

The service-role key must never be set here.

## Deploying (Vercel)

Import this repository as a Vercel project. The repository root is the app (framework Next.js, no root-directory override). Set the environment variables above for Production and Preview. `vercel.json` only pins the framework. Until `TURNSTILE_SECRET_KEY` is set, a production deployment loads but refuses sign-in on purpose.

## Database types

`vendor/supabase/database.types.ts` is generated by the platform repository (`supabase gen types typescript --linked`) and copied here; never edit it by hand. After a database change, regenerate it there, then run `npm run types:sync -- path/to/database.types.ts` here and commit the result.
